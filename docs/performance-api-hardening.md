# Производительность и ошибки API: этап 4

C09, C10, C12, C13 и C14 из аудита исходного коммита `555e68af` исправлены
и проверены локально. Рабочая ветка — `codex/fix-purchase-atomicity`. Этот этап
не включает push, развёртывание, SSH-проверку сервера или сверку с провайдерами.

## Пароли и перегрузка API — C09

Bcrypt больше не выполняется в event loop в пяти местах кабинета и четырёх
местах гостевой покупки. Асинхронные обёртки используют отдельный пул с двумя
рабочими потоками. На процесс принимается не более восьми операций суммарно:
выполняющихся и ожидающих. Место принадлежит вычислению, поэтому отмена запроса
не позволяет бесконечно накапливать работу в очереди. Общий executor asyncio
этими вычислениями не занят.

Предел 72 UTF-8 байта проверяется до постановки в очередь; формат и cost 12
существующих bcrypt-хешей сохранены. При заполнении пула кабинет отвечает HTTP
503 с `Retry-After: 2`. Гостевая покупка получает временную ошибку активации 503;
уже подтверждённая оплата не превращается из-за перегрузки в окончательный отказ.
Она остаётся доступной штатному механизму повторной активации.

Вход по email дополнительно ограничен десятью запросами за 60 секунд на аккаунт,
независимо от смены IP. Адрес нормализуется, а ключ лимитера содержит SHA-256,
не сам email. При превышении лимита возвращается 429/`Retry-After: 60`. Проверка
через Redis работает с `fail_closed=True`: его недоступность тоже ограничивает
вход. Ранее существовавший лимит по IP сохранён.

Ожидание фонового вычисления допускает изменение пользователя другим запросом.
Поэтому вход повторно проверяет хеш и версию сессии под блокировкой пользователя,
а привязка email — также email и состояние подтверждения. Сброс пароля сохраняет
блокировку на время хеширования и атомарного отзыва сессий. Создание учётных
данных для существующего гостевого пользователя также использует блокировку.
Это сохраняет защиту от гонок этапа 3 после появления новых точек `await`.

Лимиты установлены на процесс: несколько worker-процессов имеют отдельные пулы.
Они ограничивают принимаемую работу, но не заменяют измерение нагрузки и выбор
числа процессов под CPU сервера. Локальный микробенчмарк macOS/Python 3.13 с
четырьмя операциями «hash + check», bcrypt cost 12 и таймером 5 мс показал
снижение максимального запаздывания таймера с 1365,611 до 0,691 мс. Это измерение
отзывчивости event loop на локальной машине, не p95 API и не нагрузочный тест
рабочего сервера.

## Список и создание бэкапов — C10

Сканирование каталога, чтение архивных метаданных, запись небольших индексов
и retention выполняются в отдельном пуле `backup-io`: два рабочих потока,
четыре принятые задачи на процесс. Параллельные запросы списка используют одно
сканирование на экземпляр сервиса. Переполнение возвращает последний готовый
список, если он есть; без него Web API отвечает 503 с `Retry-After: 5`.

Sidecar-индекс привязан к размеру, mtime/ctime с наносекундами, device и inode.
При невозможности записать индекс работает кэш в памяти до 256 записей.
Метаданные новых архивов идут первыми и читаются потоком с пределом 1 МиБ без
распаковки на диск. Retention не читает содержимое: использует UTC-дату имени
созданного бэкапа либо mtime файла старого формата. Создание допускает одну
операцию на экземпляр сервиса и атомарно публикует готовый архив из `.partial`.

Список не является проверкой целостности полного архива. Первое чтение старого
формата может быть дорогим, хотя больше не блокирует event loop. Отмена обычного
вызова создания или планировщика ожидает защищённую внутреннюю задачу целиком.
Прямая отмена этой внутренней задачи отдельно защищена во время публикации
архива, но старые стадии `pg_dump` / `process.communicate()` и сбора snapshot
через `asyncio.to_thread` ещё допускают очистку staging до завершения фоновой
работы. Для полной гарантии корректного shutdown нужны отдельные изменения
управления subprocess и snapshot-worker; влияние этого условия на прод в этом
этапе не перепроверялось.

Смежные backup-маршруты теперь проверяют разрешённый путь через
`Path.is_relative_to`, включая цель symlink. Проверка строкового префикса
пропускала соседние каталоги с общим началом имени. Доступность Web API на
текущем проде не перепроверялась: это дополнительное исправление кода, без нового
подтверждённого продового замечания. Подробности: [backup-indexing.md](backup-indexing.md).

## Активация из меню — C12

Исправлены отсутствующий импорт функции скидки и сравнение со строкой `ACTIVE`
вместо фактического значения `active`. Под блокировкой пользователя выполняются
и выбор операции, и покупка: два одновременных callback не создают две первые
подписки. Баланс, расход, подписка и постоянное задание синхронизации панели
фиксируются одним COMMIT. Ошибка SQL, реального отложенного COMMIT или отмена
до успешного COMMIT откатывает денежную операцию.

Существующее продление также отделяет COMMIT от последующих действий. Если
оплата зафиксирована, ошибка уведомления или панели не выдаётся за неудавшуюся
покупку. Пользователь получает сообщение об оплаченной подписке и продолжающемся
подключении, а сохранённая задача доступна для повтора. Гарантия внешнего API
«ровно один раз» этим не добавляется; действуют ограничения очереди этапа 2.

## Уведомления и индекс — C13

Проверки истории уведомлений выполняются пакетами не более 500 пар
«пользователь — подписка». Пара сохраняет принадлежность записи; `NULL` в
`days_before` не превращается в ноль. Учитываются ещё не сброшенные в БД записи
текущей сессии, в том числе при `autoflush=False`. Затронутые циклы мониторинга
повторно используют загруженные подписки и ключи уведомлений вместо отдельных
запросов для каждой строки.

Миграция `0105` после `0104` добавляет неуникальный индекс
`ix_sent_notifications_lookup` по `(subscription_id, user_id, notification_type,
days_before)`. На PostgreSQL создание и удаление выполняются `CONCURRENTLY`
в autocommit-блоке Alembic. Повтор online-миграции удаляет оставшийся после
неудачного построения невалидный индекс и создаёт его заново; обычного
`IF NOT EXISTS` для такого случая недостаточно.

Индекс не меняет историю уведомлений и не удаляет дубликаты. Пакетная проверка
уменьшает число запросов, но не делает отправку конкурентными процессами
транзакционной и не гарантирует доставку «ровно один раз».

## Удаление устройства — C14

Кабинет вызывает строгий режим удаления: успех возвращается при подтверждённом
отсутствии устройства либо ответе панели 404. Неполное подтверждение проверяется
чтением всех страниц, максимум десять страниц по 1000 устройств. Некорректные
ответы, повторные страницы, меняющийся итог и неполная выборка не считаются
успехом. Старые вызовы `remove_device` без `strict=True` сохраняют свой контракт.

| Ответ/сбой панели | Ответ кабинета |
|---|---|
| 404, устройство или пользователь уже отсутствует | Успех |
| 429, 502, 503 либо временная сетевая ошибка | 503 |
| Тайм-аут или 504 | 504 |
| Другие отказы, включая 401/403 панели, неверное подтверждение | 502 |

Ошибка авторизации backend в панели не возвращается клиенту как 401 его
собственной сессии. В логах обработчика остаются тип ошибки и статус панели,
без полного тела её ответа.
