# Cardlink

Интеграция использует [официальный Bills API Cardlink](https://cardlink.link/en/reference/api).
По образцу WATA метод включён в пополнение баланса, прямые платёжные кнопки
Telegram, кабинет, гостевые покупки/подарки и продление на странице подписки.
Поиск платежей, проверка статуса администратором и статистика дохода учитывают
квитанции Cardlink. Доступные методы, их порядок и названия задаются общей
конфигурацией платёжных методов.

## Подключение магазина

До настройки Cardlink выключен. Нужны API-токен и Shop ID из аккаунта магазина.
Секреты следует хранить в конфигурации окружения сервера или защищённых системных
настройках, не в исходниках.

| Настройка | Назначение / значение по умолчанию |
| --- | --- |
| `CARDLINK_ENABLED` | Разрешить новые счета; по умолчанию `false` |
| `CARDLINK_API_TOKEN` | Bearer-токен API и ключ проверки уведомлений |
| `CARDLINK_SHOP_ID` | Идентификатор магазина |
| `CARDLINK_BASE_URL` | `https://cardlink.link` |
| `CARDLINK_DISPLAY_NAME` | `Cardlink`; название также настраивается в списке способов оплаты |
| `CARDLINK_PAYMENT_METHOD` | Пустое значение — выбор на стороне Cardlink; либо `BANK_CARD` / `SBP` |
| `CARDLINK_PAYER_PAYS_COMMISSION` | `false`: комиссия не добавляется покупателю |
| `CARDLINK_MIN_AMOUNT_KOPEKS` | `10000` (100 ₽) |
| `CARDLINK_MAX_AMOUNT_KOPEKS` | `100000000` (1 000 000 ₽) |
| `CARDLINK_LINK_TTL_SECONDS` | Срок жизни счёта, `900` секунд |
| `CARDLINK_REQUEST_TIMEOUT` | Таймаут API, `30` секунд; ограничен диапазоном 1–60 |
| `CARDLINK_WEBHOOK_PATH` | `/cardlink-webhook` |
| `CARDLINK_SUCCESS_REDIRECT_URL` | Необязательный адрес возврата после успешной оплаты |
| `CARDLINK_FAIL_REDIRECT_URL` | Необязательный адрес возврата после ошибки |

1. Сначала установить приложение и применить миграцию `evo_0111`. Она добавляет
   таблицу `cardlink_payments`, не изменяя прежние платежи.
2. Настроить токен и магазин. В кабинете Cardlink указать Result URL вида
   `https://<публичный-домен-бота>/cardlink-webhook`. При другом
   `CARDLINK_WEBHOOK_PATH` использовать этот путь. Обработчик должен быть доступен
   снаружи; после настройки проверить маршрутизацию через действующий reverse proxy.
3. Cardlink отправляет возвраты Success URL и Fail URL методом **POST**, а их домен
   должен совпадать с доменом магазина. Указать подходящие обработчики в настройках
   магазина либо через `CARDLINK_SUCCESS_REDIRECT_URL` / `CARDLINK_FAIL_REDIRECT_URL`.
   Обычная GET-страница SPA для этого не подходит. Общие `return_url` кабинета и
   страницы подписки намеренно не подставляются в запрос Cardlink. Если отдельные
   адреса не заданы, используются настройки магазина.
4. Включить Cardlink и выставить нужные название/порядок в общих настройках способов
   оплаты. Явно заданные ENV-переменные имеют приоритет над настройками в БД;
   если переключатель должен управляться через админку, не фиксировать его в ENV.
5. Проверить создание и оплату небольшого счёта в подключённом магазине, уведомление,
   баланс/выдачу покупки и повторную проверку этого же счёта. Локальные тесты используют
   подмену API Cardlink и не заменяют проверку реального магазина.

Кнопка оплаты открывает полученный `link_page_url` Cardlink напрямую. Адрес бэкенда
не используется как промежуточная платёжная ссылка. Интеграция создаёт одноразовые
счета `normal` в RUB; периодические списания не подключены.

## Подтверждение платежа

Уведомления принимаются как ограниченная по размеру форма
`application/x-www-form-urlencoded`. Подпись проверяется по исходной строке
`OutSum:InvId:API_TOKEN` с MD5, как требует протокол Cardlink. В эту подпись не входят
статус, ID счёта и валюта, поэтому одной корректной подписи недостаточно для зачисления.

Обработчик запрашивает `/api/v1/bill/status` с Bearer-токеном и сверяет ID счёта,
номер заказа, валюту RUB, тип NORMAL и сумму с локальной записью. Только `SUCCESS`
и `OVERPAID` подтверждают оплату. На баланс поступает ровно сумма локального заказа;
комиссия и переплата из уведомления не увеличивают зачисление. `UNDERPAID` не зачисляется.

Блокировки PostgreSQL защищают квитанцию и баланс от повторных уведомлений и
одновременной ручной проверки. Сбой внешнего API возвращает ошибку обработки, чтобы
Cardlink повторил уведомление. При необходимости статус можно проверить из админки
или кнопкой проверки в боте; отдельная фоновая сверка для Cardlink не добавляется.

Выключение `CARDLINK_ENABLED` закрывает создание новых счетов. При сохранённых
реквизитах уже выданные счета продолжают приниматься обработчиком. Не удалять и не
менять токен до обработки ожидающих счетов: он используется и в API, и в подписи.

Квитанции учитываются в доходе один раз, без повторного добавления пополнения и
покупки с баланса. При удалении аккаунта квитанции сохраняются с обнулёнными связями.
Автоматический downgrade миграции запрещён, поскольку он удалил бы финансовые
записи; откат приложения и базы требует отдельного плана с резервной копией.
