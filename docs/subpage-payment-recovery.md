# Счета Subpage и восстановление продлений

Исправления C03/C04/C05/C11 из аудита продакшен-коммита `555e68af`.
Реализация рассчитана на PostgreSQL. Миграция `0103` обязательна перед запуском
обновлённого приложения; в рамках разработки на рабочий сервер она не применялась.

## Заказ и оплата

До обращения к YooKassa/WATA создаётся `subpage_invoices`: владелец, подписка,
подписанный short UUID, период, сумма, валюта, комплектация тарифа и расчёт скидок.
Привязка ответа провайдера не перезаписывает состояние заказа, если webhook уже
успел его завершить. WATA сохраняет метаданные Subpage при первой записи платежа.

Подтверждённый провайдером платёж переводит заказ из `pending` в `paid` отдельным
COMMIT. Затем под блокировками пользователя, заказа и подписки одна транзакция
записывает пополнение, расход, продление, состояние `succeeded` и задачу панели.
Ошибка БД или отмена до COMMIT откатывает эту транзакцию. Заказ остаётся `paid`
и возобновляется фоновым обработчиком либо повторным webhook. Наличие DEPOSIT
само по себе не считается завершённой покупкой. Повтор после успешного COMMIT
не списывает средства и не продлевает подписку ещё раз.

Цена и комплектация проверяются повторно. При изменениях оплаченная сумма
остаётся на балансе (`credited_only`); продление по другой цене не выполняется.
Сумма WATA берётся из локального счёта, как и раньше: провайдерская сумма с
добавленной комиссией не становится суммой покупки.

Разовая скидка проверяется и потребляется под блокировкой пользователя. Несколько
счетов с одной скидкой могут быть созданы, но успешно продлить с ней сможет только
первый. Остальные оплаты зачисляются на баланс. Неоплаченный счёт не резервирует
скидку: иначе посетитель публичной страницы мог бы заблокировать её владельцу.

Несовпадение владельца, метода или идентификатора платежа отклоняется. Неподдерживаемая
валюта и неоднозначное старое начисление получают `review`, без повторного
начисления или автоматического продления.

## Синхронизация с панелью

`renewal_sync_tasks` сохраняется вместе с денежной транзакцией общего сервиса
продления. Флаги сброса трафика, устройств и синхронизации сквадов объединяются
для одной подписки; номер версии не позволяет старому обработчику закрыть новое
задание. Advisory lock PostgreSQL защищает от двух одновременных обработчиков.
Он удерживается отдельной сессией, поскольку клиент панели делает свои COMMIT.

Обработка `None`, исключений и тайм-аутов оставляет задание в БД. Сброс трафика
выполняется через API с обязательной проверкой результата: прежний вспомогательный
метод скрывает ошибки и для этого пути не используется. Сброс устройств также
требует подтверждения. Повторы имеют задержку до часа и не удаляются после пяти
попыток. Первая попытка после COMMIT ограничена десятью секундами.

Работа запускается существующим циклом `RemnaWaveRetryQueue` при старте бота и
каждые 120 секунд, даже когда старая очередь в памяти пуста. Обрабатывается до
20 оплаченных заказов и до 20 задач панели за проход. Ошибка прохода не завершает
цикл. Для восстановления необходимо, чтобы процесс бота с этим циклом работал.

Границы гарантии:

- Этот этап переводит на постоянное хранение **общий сервис продления**. Другие
  покупки и административные операции, использующие старую очередь в памяти,
  ещё не перенесены на этот механизм.
- API панели не предоставляет идемпотентный ключ для сбросов. Если панель
  выполнила сброс, но ответ потерян, повтор может выполнить его снова. Доставка
  выполняется с повторами; гарантия «ровно один внешний сброс» не заявляется.
- Уведомления и остальные необязательные события после COMMIT не являются
  частью постоянной очереди. Их доставка после падения процесса не гарантируется.
- Возобновляются заказы, для которых подтверждение оплаты уже сохранено. Поиск
  платежей, о которых провайдер вообще не сообщил приложению, сюда не входит.

## Совместимость и развёртывание

Новые статусы и принадлежность счёта читаются из PostgreSQL без TTL Redis.
API сохраняет прежние `pending/succeeded/failed` и добавляет `balanceCredited`
и `message`. Отображение этих дополнительных полей во внешней странице подписки
нужно подключить в её интерфейсе; в этом репозитории меняется контракт backend.

Массового переноса исторических счетов нет. При позднем webhook старый счёт
восстанавливается из проверенных метаданных платежа. Если исходная комплектация
неизвестна, новая оплата зачисляется на баланс. Существующее начисление при
неизвестном результате требует проверки; оно не считается ни новой оплатой,
ни доказанным продлением. Старый `succeeded` из Redis принимается только вместе
с подходящей завершённой транзакцией. Если исчезли и кеш, и все пригодные
метаданные, восстановить исходный заказ автоматически невозможно.

При будущем развёртывании сначала применить Alembic `0103`, затем обновить все
процессы приложения. Не держать старые и новые обработчики платежей одновременно:
старый код не знает о новом состоянии выполнения. Миграция только добавляет две
таблицы и не меняет существующие балансы или подписки. Downgrade намеренно
запрещён при наличии `pending/paid/review` или незавершённых задач панели. При
откате приложения таблицы с такими данными следует сохранить.

## Проверка

Как подготовить отдельную локальную PostgreSQL и переменную `TEST_POSTGRES_URL`:
[проверка атомарности](testing-purchase-atomicity.md). Команда для обеих стадий:

```sh
uv run pytest tests/integration/test_purchase_atomicity.py \
  tests/integration/test_subpage_recovery.py \
  tests/integration/test_renewal_sync_recovery.py \
  tests/integration/test_payment_recovery_migration.py -q
```

Проверяются реальные блокировки, ошибки SQL/COMMIT, отмена и потерянный ответ,
параллельные уведомления обоих провайдеров, повтор разовой скидки, изменение
цены/устройств/сквадов, поздняя оплата без Redis, восстановление через пустую
фоновую очередь, конкурирующие задачи панели, подтверждение сбросов и отказ
удаления незавершённых заказов при downgrade. Внешние API подменены; реальные
платежи и рабочая панель этими тестами не вызываются.
