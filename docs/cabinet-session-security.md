# Отзыв сессий и WebSocket кабинета

Этап 3 аудита коммита `555e68af`: C06, C07, C08 и серверная часть C15.
Изменения подготовлены локально. Рабочий сервер, прокси и фронтенд не обновлялись.

## Сброс пароля

Миграция `0104` добавляет `users.cabinet_auth_version` с начальным значением 0.
Access, refresh и guest auto-login JWT содержат эту версию. HTTP-зависимости,
refresh, auto-login и оба WebSocket-протокола сверяют её с записью пользователя.
Старые JWT без поля принимаются как версия 0 только до первого сброса пароля.
Миграция не меняет пароли, балансы или подписки и сама не завершает все сессии.

Сброс блокирует пользователя и одной транзакцией меняет хеш, погашает reset-токен,
повышает версию, отзывает все refresh-токены и удаляет неиспользованные WS-билеты.
Два запроса не могут одновременно использовать один reset-токен. Ошибка SQL,
отложенного COMMIT или отмена до успешного COMMIT откатывает все изменения.

Refresh и сохранение новой сессии также сначала блокируют пользователя, затем
строки токенов. Это устраняет гонку со сбросом. Если вход уже проверил старый
пароль, но сброс произошёл до сохранения его сессии, сохранение отклоняется.
Повторное сохранение токена не снимает с него существующий отзыв.

Область изменения — восстановление пароля. Существующий logout по-прежнему
отзывает указанный refresh-токен; он не превращён в выход со всех устройств.
Свежая авторизация через самостоятельный доверенный способ, например Telegram,
остаётся возможной. Уже выполняющийся HTTP-запрос, прошедший проверку до сброса,
не отменяется задним числом.

## Контракт пароля

Регистрация, привязка email, вход и сброс проверяют предел bcrypt — 72 UTF-8 байта.
Превышение даёт HTTP 422 до хеширования вместо HTTP 500. Например, 36 букв `я`
занимают 72 байта, а 37 — уже 74. Минимальная длина нового пароля осталась 8
символов. Пароль не обрезается; существующие хеши bcrypt 2a/2b совместимы.

Синхронная работа bcrypt в event loop (C09) относится к следующему этапу;
это исправление меняет проверку ввода, а не исполнитель вычислений.

## WebSocket-билет и срок сессии

Новый browser-контракт:

1. Выполнить `POST /cabinet/ws/ticket` с действующим `Authorization: Bearer …`
   и обычным браузерным Origin. Ответ: `ticket`, `expires_in: 30` и
   `Cache-Control: no-store`. Фактический срок дополнительно ограничен сроком JWT.
2. Сразу открыть `/cabinet/ws?ticket=…` с того же Origin. Билет удаляется атомарно
   через PostgreSQL `DELETE … RETURNING`; повторное использование невозможно,
   в том числе между разными процессами приложения.
3. На переподключение получать новый билет. При HTTP 401 обновить access-токен
   штатным refresh-механизмом или повторно войти.

В БД хранится только SHA-256 случайного билета. Срок — максимум 30 секунд.
Одновременно допускается до 10 неиспользованных билетов на пользователя.
Origin должен соответствовать `CABINET_URL` или явной записи в
`CABINET_ALLOWED_ORIGINS`; `*` не разрешает произвольные WS-origin.

Долгоживущий JWT в query-параметре `token` больше не принимается. Серверная часть
готова и проверена, но **C15 ещё требует изменения рабочего фронтенда**.
Исходников его рабочей ветки в этой папке нет; нельзя считать общую ссылку на
upstream из README подтверждённым исходником прода. Развёртывание этого этапа
без переключения клиента прервёт старые WS-подключения на переподключении.
Запрос старого клиента с JWT в URL всё ещё может попасть в журнал прокси до
отказа backend, поэтому переход клиента и политика журналирования нужны вместе.

Пример только для адаптации существующего клиента (не замена его refresh-логики):

```javascript
async function connectNotifications(apiBase, accessToken) {
  const response = await fetch(new URL('/cabinet/ws/ticket', apiBase), {
    method: 'POST',
    headers: { Authorization: `Bearer ${accessToken}` },
    cache: 'no-store',
  });
  if (!response.ok) throw new Error(`WebSocket ticket: HTTP ${response.status}`);
  const { ticket } = await response.json();
  const url = new URL('/cabinet/ws', apiBase);
  url.protocol = url.protocol === 'https:' ? 'wss:' : 'ws:';
  url.searchParams.set('ticket', ticket);
  return new WebSocket(url);
}
```

Обычный WS закрывается по `exp`, отзыву версии, блокировке пользователя и отзыву
прав администратора. Неактивное соединение проверяется каждые 30 секунд; перед
отправкой данных проверка выполняется заново. Административные события требуют
актуального `tickets:read`, включая RBAC/ABAC, доверенный источник admin-email и
IP с учётом настроенных доверенных прокси. Проверка и отправка ограничены тремя
секундами. Лимиты: 5 подключений на пользователя и 1000 на процесс. Неактивный
клиент не может отложить проверку сессии потоком некорректных сообщений.

Support/mobile WS сохраняет прежний bearer-протокол и дополнительно проверяет
версию при подключении, командах, рассылке и ожидании новых сообщений. Старый
access-токен нельзя использовать для reauthenticate после сброса пароля.

Список соединений и рассылка остаются внутри процесса. Redis pub/sub для
межпроцессной доставки в этот этап не добавлен. Отзыв сессий работает между
процессами через общую PostgreSQL.

## Миграция и проверка

Перед новым кодом требуется миграция `0104` после `0103`. Downgrade разрешён до
первого отзыва; при ненулевой версии он отклоняется, чтобы не потерять сведения
об отзыве. Безопасный откат требует сохранения проверки версии и в коде: одного
сохранения столбца недостаточно. На прод миграция не применялась.

Настройка отдельной loopback PostgreSQL описана в
[инструкции к платёжным тестам](testing-purchase-atomicity.md).

```sh
uv run pytest tests/integration/test_cabinet_session_security.py \
  tests/integration/test_cabinet_auth_migration.py tests/cabinet -q
```

Проверки используют реальные транзакции, блокировки и COMMIT PostgreSQL, а также
ASGI WebSocket-соединения. Охватываются гонки reset/refresh/login, одноразовость
reset-токена и билетов, отзыв старых JWT без версии, сохранение bcrypt-хешей,
закрытие сокета без клиентского ping, смена прав, медленный получатель и миграция.
Внешние OAuth, Telegram, платёжные сервисы и рабочая панель не вызываются.
