# Проверка атомарности покупки и продления

Тесты `tests/integration/test_purchase_atomicity.py` используют настоящую PostgreSQL
и проверяют C01/C02 из аудита коммита `555e68af`. Расчёт цены и CRUD выполняются
реальным кодом; авторизация Telegram, панель, корзина и внешние события подменены.

Нужна отдельная локальная PostgreSQL и установленные зависимости разработки,
включая `asyncpg` и поддержку SQLAlchemy asyncio (`greenlet`). На боевой базе тесты
не запускать. Проверка допускает только loopback-адреса, создаёт схему со случайным
именем `test_atomic_*` и удаляет только эту схему при завершении. Пользователю БД
нужно право создавать схемы. Отдельно очищается тестовая схема между сценариями.

Пример запуска из корня репозитория:

```sh
TEST_POSTGRES_URL='postgresql+asyncpg://test_user:test_password@127.0.0.1:5432/test_db' \
BOT_TOKEN='123456789:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA' \
uv run pytest tests/integration/test_purchase_atomicity.py -q
```

Без `TEST_POSTGRES_URL` интеграционные тесты пропускаются. Глобальный conftest при
заданной переменной загружает настоящий asyncpg вместо заглушки для unit-тестов.

Проверяемые сценарии:

- новая покупка, продление активной/истёкшей подписки и конвертация триала;
- сохранение и оплата дополнительных устройств, выбор подписки в multi-tariff;
- первый оплаченный день суточного тарифа и полная промоскидка;
- отказ от неподдерживаемого периода до списания;
- ошибки SQL при создании/изменении подписки, записи расхода и очистке триалов;
- отказ настоящего COMMIT из-за отложенного ограничения PostgreSQL;
- отмена задачи и реальный таймаут блокировки строки после списания;
- атомарность записи стоимости серверов вместе с балансом и продлением;
- запрет изменения чужой подписки;
- конкуренция за последний остаток и сохранение двух оплаченных периодов;
- чтение подтверждённого состояния из другой сессии перед внешними событиями.

Первый этап не меняет правила старых счетов Subpage, идемпотентность webhook и
очередь синхронизации панели. Потеря ответа после уже выполненного COMMIT требует
отдельного идентификатора заказа и восстановления; откат транзакции не заменяет
этот механизм. Эти вопросы относятся к следующему этапу C03/C04/C05/C11.
